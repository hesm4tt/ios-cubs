# Booting iOS on the Pixel 11 (CUBS): checklist

Last updated: 2026-11-03 (the stage table, the "Dual boot, buttons, network (2026-11-03)" section at the end and the sections from "Fast SpringBoard" on are current; older sections keep the date they were written)

Status as of 2026-11-03 (the detailed sections below are in the order they were written, newest last). Legend: **[x]** done and proven on the phone · **[~]** started or partly working · **[ ]** not started.

The goal (from [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md) §1): the phone reaches the **iOS lock screen**, the display and touch work, it stays responsive for 5 minutes, and it can go back to Android. The boot is RAM-only (`fastboot boot`); the system image is read from the spare `modem_a`/`modem_b` partitions into RAM.

Boot chain:

```
Unlocked bootloader → fastboot boot (stock-shaped 64 MiB boot image) → CUBS ARM64 shim
  → XNU kernel (HackiOS 8796.121.2) → RAM root + diagnostic init → full iOS 16.5 system
  → display + touch → lock screen
```

## 6. Getting the full iOS image onto the phone

## SpringBoard in ~2.5 min instead of ~16 (2026-11-02) — the first-boot delay is solved
Root cause, in two parts, both inside libMobileGestalt (iOS 16.5 / 20F66):
1. MobileGestaltHelper denied lsd/wifid/... the protected key `9/J7LY7zuYSGW1BcSTRpOw` ("pid N (lsd) IS NOT appropriately entitled", error 9: the entitlement lookup fails on this port), so every caller retried forever and the real helper respawned in a crash loop. The stub `mghelper` (mghelper.m) answers the NSXPC call `getServerAnswerForQuestion:reply:` itself: `_MGSetServer(1)` then the plain `MGCopyAnswerWithError(q)` (no caller check) and replies `@{@"answer": a}`. The launchd job is pointed at it with `JOB_PROGRAM="com.apple.mobilegestalt.xpc=/redwood/bin/mghelper"` (mkjobs.py patch); launchd refuses non-platform service binaries, so the kernel marks `mghelper` platform (kern_exec.c) and csops reports it so (kern_proc.c).
2. MGIOKitSupport waits up to 5 s per question for IORegistry services (IONetworkController, AppleDiagnosticDataAccessReadOnly, ...) that this port does not have; lsd asks hundreds of such questions. `libmgpatch.dylib` (mgpatch.c, injected into lsd and SpringBoard) patches the run-loop timeout instruction (`scvtf d0,w8` at MGSetAnswer+0x1A9DC) to `fmov d0,xzr` at runtime.
Result: `Telling "com.apple.springboard" that it can start immediately` at launchd+145 s, panel "lit src" 18568 (home screen content) instead of 449 (boot logo).
Reproduce: INJECT line `/redwood/bin/libmgpatch.dylib lsd SpringBoard`, extra files `mghelper libmgpatch.dylib`, env JOB_PROGRAM as above.

## How the iOS compositor draws today, and the way to put it on the GPU (2026-11-02)
- CoreAnimation's render server (backboardd) draws with Metal, else OpenGL ES (EAGLContext), else its own software rasterizer. In this port, with no `GL=1` image, it uses the software rasterizer (the home screen above). userland/src/eagl.c replaces EAGLContext with an OpenGL ES library behind the `redwood_gl.h` interface; today that library is Mesa OSMesa (gl_osmesa.c, softpipe/llvmpipe), upstream's phones use freedreno (Adreno) in process. userland/src/redwoodmetal.m + tools/mesa/air (the `rwa_*` contract, ~30 functions) is the Metal-side equivalent.
- The Pixel's GPU (PowerVR) is only reachable from Android, so both are the same shape: a client library inside iOS (gl_osmesa.c-style GL ES library, or an `rwa_*` backend) that forwards over the ring (PA 0xab2000000, see mtlsrv) to a server on Android that runs the work on the PowerVR (GLES through EGL for the GL route; metal2vulkan for the rwa route) and returns/ presents the pixels.
- Recommended: GL ES forwarding first (CoreAnimation's GL path uses a few dozen calls, shaders are GLSL text that Android's driver compiles, framebuffer = IOSurface memory), results straight into the scanout buffer; then the Metal route reuses the same plumbing.
- Run recipe with the fast-boot pieces: `~/run_ios.sh NAME [WAIT]` on the Mac (JOB_PROGRAM, inject list, mghelper + libmgpatch).

## GL forwarding: where the frame time goes (2026-11-02, late)
- Ring traffic is no longer the limit: uploads send only changed bands into a server-side GPU texture cache (OP_CACHE_*), readbacks return only changed bands against the server's previous readback of the same texture (OP_READ_PIXELS_DELTA, client shadows per texture, a full one every 64th). 1 sync round trip per frame instead of ~25; ring overflows 14k -> 6.
- Frame time stays ~41 ms because the server's glReadPixels of the 1125x2436 frame costs ~21 ms (ANGLE on Vulkan, measured separately from glFinish) plus ~6 ms glFinish and ~5 ms of uploads from cache. ## SOLVED: the audio-server freeze (2026-11-04) - mediaserverd needs nanoregistryd
- Method: the kernel prints the saved user registers and the frame-pointer chain of every thread of mediaserverd/SpringBoard (`cubs_threads_after=N`, `cb_ustack` in `cubs_touch.c.inc`); the addresses are matched with the image list of the dyld shared cache of the iOS volume (`ios165/.../dyld_shared_cache_arm64`, header images table; the slide is found by requiring that the trap-stub PCs land in libsystem_kernel: here 0x4f08000). Result: mediaserverd's main thread waits in a semaphore under `NanoRegistry+0x4dc4 <- +0x33e4 <- +0x76ec` (a synchronous request to `com.apple.nano.nanoregistry.paireddeviceregistry`), and SpringBoard's blocked threads wait in `libxpc <- CoreMedia` for mediaserverd.
- Fix: put the job `com.apple.nanoregistryd` (and `com.apple.nanoregistrylaunchd`) into the job list next to mediaserverd. Now the panel stays lit (lit src ~18.6k at 100-260 s), SpringBoard comes up, `camera_avtest` lists "Back Camera" and "Front Camera" with their formats through AVFoundation, and sound_test finds the audio session.
